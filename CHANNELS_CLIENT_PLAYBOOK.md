# Playbook: новый Channels-клиент NeuroStaff

Читай это, если разворачиваешь нового клиента по образцу Ашет (Ольги) — личного
ИИ-ассистента через **Claude Code Channels** на подписке самого клиента (Pro/Max), а не через
платный API-ключ платформы. Это отдельный продукт внутри NeuroStaff, не часть основной
Python+Postgres+pgvector платформы (Марина/Артём/Тимур/Алексей/Амина).

## Зачем это отдельный путь, а не как остальные агенты

Платформенные агенты — это наш код (`worker.py`), который сам вызывает LLM API и сам строит
system prompt на каждое сообщение. Channels-клиент — это **чужой процесс**, обёрнутый
`claude --channels` под подпиской клиента: мы не вызываем LLM сами, не видим ответ до его
отправки (Telegram-плагин — чёрный ящик). Отсюда всё специфичное ниже: нельзя просто
переиспользовать код платформы, нужны отдельные механизмы контроля постфактум.

## Быстрый старт

```bash
cd /Users/andrejorlov/Documents/my-project/ashet-olga
./new_channels_client.sh <client-slug> <telegram-bot-token>
```

Скрипт сам делает: папку проекта, git-репозиторий, копию Dockerfile/entrypoint.sh/
companion.js/transcribe.js, Railway-проект+сервис, публичный домен для companion.js, деплой.
В конце печатает точные команды для того, что не автоматизировано (см. ниже).

**Обязательно вручную, клиент/владелец делает сам** (не автоматизируется принципиально):
1. Логин в его личный Claude Pro/Max (OAuth) — через Railway веб-консоль (Settings → Console,
   у неё настоящий pty; `railway ssh` из терминала не работает, `no_ssh_key`/зависает).
2. Пейринг Telegram-аккаунта клиента (доказывает владение аккаунтом).
3. Volume на Railway — `railway volume add` падает багом CLI на любых флагах (воспроизведено
   и на 5.15.0, и на 5.26.0) — только через веб-дашборд: канвас → Add → Volume.

Каждый пункт закрывает реальную дыру, найденную и исправленную на Ашет — не делать "потом".

Пункты 4 и 6 требуют **уникальных секретов на каждого клиента**. Скрипт генерирует их,
сохраняет в локальном `.env` клиента и выставляет на его Railway-сервисе; те же значения
нужно добавить на neurostaff как `PUBLISH_GATEWAY_SECRET_<SLUG>` и
`MEMORY_GATEWAY_SECRET_<SLUG>`. Общими остаются только `TG_API_ID`/`TG_API_HASH` (если
клиент явно подключает Telegram Stories).
Пункт 4 (client-approval) и пункт 7 (Telegram-канал) заодно требуют на **neurostaff**
`TELEGRAM_BOT_TOKEN_<SLUG>` (тот же токен бота клиента) и `CLIENT_CHAT_ID_<SLUG>` — без них
approve падает только на резервный override админа.

Точные команды `railway variable --set ...` — в конце вывода `new_channels_client.sh`.

## Архитектура памяти (почему НЕ файл на диске)

Платформенные агенты имеют 4-уровневую память в Postgres (`worker.py`, `memory/episodic.py`,
`memory/semantic.py`): buffer / episodic (summary) / semantic (pgvector) / procedural (навыки
из БД). У Channels-клиента:

- **Уровень 1 (buffer)** — закрыт бесплатно: сам Claude Code хранит JSONL-транскрипт сессии.
- **Уровень 4 (procedural)** — закрыт бесплатно: CLAUDE.md клиента, версионируется в git.
- **Уровни 2-3** — требуют `memory_gateway.py` (см. пункт 6 таблицы выше). Клиент никогда не
  получает креды БД — только URL+секрет к гейту, который сам пишет/читает в **изолированную**
  БД `channels_memory` на RUVDS (не общую БД платформы — блокирует SQL-инъекцию через сам
  гейт от дотягивания до данных других клиентов).

Раньше (до 12.07.2026) вместо уровней 2-3 был грубый суррогат — файл `/data/memory/olga.md`
на volume, читаемый/дописываемый агентом вручную. Не повторять для новых клиентов — сразу
подключать memory-gateway (пункт 6).

## Известные баги entrypoint.sh — не наступать заново

Три независимых бага в одной строке запуска (`Dockerfile`/`entrypoint.sh` уже содержат фикс,
просто зная причину — не сломать при правке):

1. `--dangerously-skip-permissions` запрещён от root → нужен непривилегированный юзер
   (`node`, уже есть в `node:20-bookworm-slim`, не создавать своего).
2. `su -p node` без явного `HOME=` — тихий баг: `-p` сохраняет `$HOME=/root` от родителя,
   `claude` резолвит `~/.claude/...` в `/root/...`, плагин Telegram молча не стартует.
   Фикс — `env HOME=/home/node su -p node -c ...`.
3. Без реального pty падает с `Input must be provided either through stdin or as a prompt
   argument`. Обходится через `script -qec "..." /dev/null`.

## Самый коварный баг — не диагностировать вживую работающий процесс вторым запуском

Если во время диагностики параллельно с продакшн `--channels` (уже слушает Telegram) запустить
ВТОРОЙ `claude --channels` с тем же токеном бота — оба конкурируют за long-polling, оба
ломаются, выглядит как проблема прав/окружения. Проверять живость безопасно:
`curl -s https://api.telegram.org/bot<TOKEN>/getWebhookInfo` (смотреть `pending_update_count`),
никогда не `getUpdates`.

## Instagram/Buffer — лимит подписи считает эмодзи не так, как кажется

Buffer отклоняет пост (`Invalid post: Instagram posts cannot exceed 2196 characters`) даже
когда обычный подсчёт символов показывает меньше лимита — реальный подсчёт идёт по UTF-16
code units JS-строки, а составные эмодзи (👨‍🔬, флаги, ZWJ-последовательности) весят 2-7 единиц
каждая, не 1. Текст с эмодзи почти на каждой строке может выглядеть на ~2140 символов и всё
равно упасть. CLAUDE.md каждого клиента с доступом к Instagram должен сам прикидывать риск ДО
отправки заявки (`>15 эмодзи` ИЛИ `>~1800` символов обычного текста → предупредить клиента и
предложить сократить, а не отправлять и ловить fail постфактум) — раздел "Проверка длины
подписи" в `ashet-olga/CLAUDE.md` копируется как есть.

## OAuth-сессия истекает без предупреждения — дирижёр не может починить сам

Найдено вживую 16.07.2026 на Амине: OAuth-токен, посеянный из Keychain владельца
подписки (см. `capability_claude_code_channels_deploy.md`), истёк/стал невалиден. Клиент
получил ровно один системный ответ `Not logged in · Please run /login` вместо реальной
обработки сообщения — и тишину дальше. `getWebhookInfo` при этом чистый (бот жив,
`pending_update_count: 0`), поэтому старый health-check (пункт 3 таблицы выше, ловит только
конфликт поллинга) это не поймал бы вообще — нужен отдельный детектор.

**Детекция** — `companion.js::detectAuthExpired`: смотрит последнюю по времени
assistant-реплику в JSONL-транскрипте, ищет `Not logged in`/`Please run /login`. Отдаёт
`auth_expired`/`auth_expired_snippet` в `/status` рядом с `contamination_incidents`. Как только
сессия оживает (новая нормальная реплика после пересева токена) — флаг сам гаснет, ничего не
нужно чистить руками.

**Алерт** — `super_bot.py::_check_channels_auth_expired(context, slug, display_name, status)`,
общая функция на всех клиентов (не copy-paste per-client, как остальные health/quality-джобы) —
потому что чинить это **дирижёр не может в принципе**: у процесса на Railway нет доступа к
Keychain на локальной машине Андрея, откуда единственный раз добывается валидный токен.
Вызвать её нужно из `_<slug>_quality_job` сразу после проверки `status.get("ok")` — см. шаг 3 в
выводе `new_channels_client.sh`. Алерт админу приходит один раз на эпизод (латч
`_channels_auth_expired_latch`, сбрасывается сам, когда `auth_expired` снова станет `false`) и
содержит точную инструкцию — какие переменные выставить на Railway (`SEED_CLAUDE_CREDENTIALS`,
`FORCE_RESEED=1`) и что это должен сделать не дирижёр, а Клод/Андрей руками, из сессии с
доступом к Keychain.

**Восстановление** (делает Клод в активной сессии на Mac Андрея):
```bash
security find-generic-password -s "Claude Code-credentials" -w   # свежий токен
railway variable --service "<slug>" --set "SEED_CLAUDE_CREDENTIALS=<токен>" --set "FORCE_RESEED=1"
# дождаться редеплоя, проверить (getWebhookInfo чистый + логи без "Not logged in")
railway variable delete --service "<slug>" SEED_CLAUDE_CREDENTIALS
railway variable delete --service "<slug>" FORCE_RESEED
```
`entrypoint.sh`-шаблон уже содержит guard на `SEED_CLAUDE_CREDENTIALS`/`FORCE_RESEED` по
умолчанию для каждого нового клиента (см. Dockerfile/entrypoint.sh выше) — ничего добавлять в
сам контейнер не нужно, только выставить переменные и передеплоить.

**Ограничение, не решено:** это НЕ предотвращает истечение токена (срок жизни OAuth-сессии
контролирует Anthropic, не мы) — только сокращает время простоя с "непонятно почему клиент
молчит" до "дирижёр сказал, что переключить" в течение одного цикла `_quality_job` (до 15 мин).

## Когда усложнять автоматизацию (не раньше)

Текущий вариант (shell-скрипт `new_channels_client.sh`) — сознательный выбор при малом числе
клиентов. При **3-м платном Channels-клиенте**:
- обобщить дирижёрский мониторинг (сейчас per-client `ASHET_*` переменные) на список клиентов
- рассмотреть переход с варианта A (скрипт-провижинер) на вариант B (оркестратор поверх
  Railway API внутри `super_bot.py`)
